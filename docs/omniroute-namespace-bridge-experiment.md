# OmniRoute namespace bridge — design-only experiment

Current decision: `OMNIROUTE_DEFER / UNRESOLVED_SECURITY_BOUNDARY` (2026-10-25). These files are **not installed or activated**. They are a falsifiable transport fixture, not an OmniRoute or Phi integration. The earlier design-only analysis below remains historical; the live trust-boundary finding follows.

## Main trust-boundary decision — A versus B

**Actual Phi boundary.** Phi/Pi and trusted extension/controller code run as UID 1000 on the host, not inside Bubblewrap. Autonomous Worker commands (`safe_exec`) and verification use `scripts/sandbox-run.sh`; Tester has no general command tool and its verification uses a read-only sandbox. The wrapper mounts a disposable worktree, private runtime state/browser directories, fresh home/tmp/etc and read-only `/usr`, but no host `/run` or normal home, and unshares network/PID/mount and other namespaces. It applies to descendant commands and shells. Worker host-side file edits are guarded to its worktree, not placed in Bubblewrap. Browser, web, MCP/control-plane and installed extensions are host-side trusted operations. Project trust and ResourceFS constrain selected paths/resources; neither turns arbitrary same-UID host processes into trusted Phi children or controls AF_UNIX connections. LPAC is a Windows boundary, not this Linux socket boundary. See `docs/security.md`, `scripts/sandbox-run.sh`, `extensions/safe-exec.ts`, `platform/shared/coding-execution.mjs` and the Worker/Tester role definitions.

**Runtime discrimination, not documentation alone.** `tests/omniroute-bridge-boundary.test.mjs` creates only disposable, credential-free Unix sockets. With the same worktree/runtime-state/browser bind arguments used by the Linux command wrapper, arbitrary Python, a shell child, unlink, bind and a workspace symlink could not reach or replace a host socket; its device/inode stayed unchanged. A distinct same-UID host process connected to that socket, and another replaced a user-owned `0600` socket pathname with a new `0600` socket. Node's built-in `http.get({socketPath})` also exchanged HTTP with a disposable socket. These prove the **particular Bubblewrap command boundary**, not that every Phi-spawned host process or unrelated UID1000 process is confined. They do not prove actual systemd activation or OmniRoute health.

| Candidate | Effective guarantee | Missing guarantee / result |
| --- | --- | --- |
| **A — user manager + existing sandbox** | The tested command subprocesses and shell descendant cannot see the host socket path, connect or replace it. The wrapper requests a private network namespace; the existing sandbox test denies one IPv4 external probe. | IPv6 egress was not independently probed in this turn. The Pi host, trusted extensions, browser/control-plane processes and unrelated same-UID processes remain outside that wrapper. A user-owned pathname can be replaced by another same-UID process. A alone does **not** meet anti-spoof or Phi-only access. |
| **B — protected system socket** | A system-manager socket and ancestor owned by root, with a narrow group/mode for Phi and a separately unprivileged fake backend, would remove same-UID *pathname replacement* authority. Actual socket inode, systemd unit/cgroup, namespace and backend listener would still need fresh runtime binding. | Granting UID1000 access via its group also grants other processes of that UID access. Neither filesystem mode nor `systemd-socket-proxyd` identifies an authorized Phi process among them; the proxy does not authenticate HTTP requests. Same-UID unauthorized use and the policy response remain unresolved. No root-owned unit/socket has been installed or tested. |

The Linux pathname permission and peer-credential mechanics are described by [unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html). [systemd.socket(5)](https://www.freedesktop.org/software/systemd/man/262/systemd.socket.html) distinguishes system-manager root ownership from user-manager ownership and exposes `SocketUser`/`SocketGroup`/`SocketMode`; mode bits are not per-process identity. A separate UID for the backend is useful for limiting backend authority, but does not by itself distinguish Phi from another UID1000 client. Backend executable, listener fd, start identity, cgroup and namespace attestation remain mandatory. A root-owned socket would require a separately approved host operation; no new privileged service is authorized here.

**Transport.** Node's [HTTP client](https://nodejs.org/api/http.html) supports `socketPath`, and the local fake-socket test exercised it. The active `extensions/omniroute.ts` does not: it registers only the ordinary `openai-completions` TCP-style `baseUrl`. Installed Pi 0.87.1 exposes provider-scoped `streamSimple`; the Pi OpenAI-completions adapter passes `options.fetch` to its SDK. A future minimal change could delegate only the OmniRoute provider stream to the existing Pi adapter with a scoped Unix-socket fetch transport, preserving model routing. This is a design candidate, not implemented compatibility: streaming, cancellation, timeouts, SDK behavior and connected-peer attestation need independent tests. No custom JavaScript proxy is indicated because official `systemd-socket-proxyd` already provides the cross-namespace forwarding function. Unix peer validation of the **proxy** must not be mistaken for attestation of the OmniRoute process behind it.

**Minimum future host experiment, requiring a new explicit approval.** Stage only hash-checked fake code and unit files in a root-owned, non-replaceable temporary directory, refusing preexisting names. Use a root-owned system-manager `.socket` with root-owned ancestor and explicitly narrow group/mode; use `systemd-socket-proxyd` and an unprivileged, separately identified fake backend sharing a private network namespace. Do not use the mutable worktree file as system-service code. Observe that a trusted Phi-UID client gets the fake response only after activation; a sandboxed tool and a same-UID host substitute cannot replace the root-owned socket. Correlate the connected socket inode and socket unit with proxy PID/start time/cgroup/netns, then backend listener fd/inode with backend PID/start time/cgroup/netns; fail on any mismatch or foreign HTTP 200. Explicitly attempt a *different same-UID host client connection*: with filesystem mode alone it is expected to succeed, so this gate cannot PASS a Phi-only policy without a separately chosen authorization mechanism or an explicit policy that permits that class. Test IPv4/IPv6 host reachability and reserved-address egress from inside the private namespace, concurrency, timeout, crash, and exact-unit cleanup; fail closed on ambiguity. No provider, credentials or OmniRoute are used. A result proving only local mode A cannot certify provider-egress mode B. The current Main decision does not authorize installing or running this host experiment.

**Trade-off.** B is the smaller credible *integrity* candidate once A's gap is acknowledged: official systemd primitives and no custom proxy. It adds system-unit ownership/cleanup, a host-operator approval boundary and a separately maintained Linux unit; same-UID client authorization would add further security complexity. Cold activation includes backend startup (historical isolated OmniRoute readiness was about 3 seconds), but bridge latency has not been benchmarked. Windows LPAC/named-pipe transport would need a separate design; these Linux unit files prove nothing on Windows. Because the required treatment of a non-Phi same-UID client is unresolved, **neither A nor B currently satisfies the full security contract**; keep OmniRoute deferred/manual-only and stop before host activation.

## Observed inputs

- Host systemd is 262; `/usr/lib/systemd/systemd-socket-proxyd` exists. The official systemd 262 example uses a host-facing `.socket`, `systemd-socket-proxyd` with `JoinsNamespaceOf=backend.service` and `PrivateNetwork=yes` on both proxy and backend: [socket-proxyd](https://www.freedesktop.org/software/systemd/man/262/systemd-socket-proxyd.html), [unit namespace semantics](https://www.freedesktop.org/software/systemd/man/262/systemd.unit.html). The previous user-unit experiment did **not** demonstrate joining the namespace; whether this exact arrangement works on this host remains UNKNOWN. User-manager `PrivateNetwork` depends on usable unprivileged user namespaces.
- Protected OmniRoute 3.8.50 is root-owned at `/opt/phi/omniroute/3.8.50/AppRun`; its prior headless isolated smoke reached loopback health and exited cleanly, but that does not prove this bridge. The launcher can spawn descendants; an HTTP 200 alone cannot identify the actual listener. Its AppRun may add `--no-sandbox` when `unshare -Ur` fails. Packaged server uses TCP `PORT`/`HOSTNAME`; source inspected locally did not establish direct Unix-socket or `LISTEN_FDS` support. This is absence of evidence, not a proof of unsupported behavior.
- Phi's current `extensions/omniroute.ts` registers `openai-completions` with a TCP-style `baseUrl` placeholder. Pi 0.87.1's provider API exposes custom `streamSimple`, while the current built-in OpenAI adapter constructs an SDK client with `baseURL`. No existing Phi Unix-socket transport is implemented or tested; a custom handler would be a separate scoped change, not an implicit `baseUrl` substitution.
- OmniRoute may perform update, leaderboard and credential-health network activity at startup. Existing egress variables or the previously ineffective user-unit `IPAddressDeny` rule are not an effective proof of no egress. DBus/IPC and all child-process needs in the proposed service arrangement are UNKNOWN.

## Uninstalled fixture

`tests/fixtures/omniroute-namespace-bridge/` contains a credential-free loopback HTTP backend, private filesystem socket, official `systemd-socket-proxyd` service and same-namespace backend service. The socket is `%t/phi-bridge-probe/proxy.sock`, directory `0700`, socket `0600`; it has no host TCP listener. Both services request `PrivateNetwork=yes`, `PrivateTmp=yes`, `NoNewPrivileges=yes`, and no automatic restart. The proxy requires and orders after the backend, then joins its namespace. This is a test of the official mechanism, not a proposed production unit or client authority. The backend fixture path is deliberately tied to this local development worktree; it must be checked before any separately approved host experiment.

Static checks: `systemd-analyze verify` on the three unit files returned 0; `node --test tests/omniroute-namespace-bridge.test.mjs` returned 3/3; Python AST and package validation are recorded in the ledger. No unit was copied, enabled, started, or connected to; no process, namespace, socket or packet observation is claimed from these checks.

## Single discriminating host experiment, **not authorized or executed here**

If Main later chooses a bounded host run, use only the fake backend and a fresh disposable user-manager unit namespace; never OmniRoute, credentials or provider calls. Before installation, pin exact fixture hashes, confirm `PrivateNetwork` and `JoinsNamespaceOf` user-manager support, inspect unit search paths and preexisting unit/socket names, and refuse collisions. Install temporary copies only after separate authority. Start the `.socket` alone; assert proxy/backend absent. On a single `curl --unix-socket ... http://localhost/__phi_bridge_probe`, assert both units start, response schema matches, and the returned PID equals the backend MainPID **as one input**, not as sufficient identity proof.

Identity proof must additionally bind unit InvocationID/cgroup/MainPID/start ticks to `/proc/<pid>/ns/net`; require proxy and backend namespace inodes equal and different from host. Map backend TCP listener inode in `/proc/<pid>/net/tcp` to an fd of the current backend process or its same-cgroup child; map the connected Unix listener to the socket unit/proxy and recheck identities before and after each request. Refuse wrong PID, changed start ticks/cgroup/namespace/inode, unrelated owner, substituted Unix socket and any host TCP listener on 20128. An unrelated HTTP 200 is a failed identity test. Do not rely on `nsenter`, which was denied in the earlier experiment.

Then test concurrent requests, bounded client timeout, backend crash before/during a request, reactivation behavior, foreign host listener on the same TCP port, IPv4 and IPv6 direct host reachability (must fail), and network namespace route/interface state. An IPv4/IPv6 egress denial test may target only reserved non-provider addresses, under a separately approved network observation method; do not claim zero egress from a config line or a single packet probe. Stop the exact units, remove only owned temporary unit files/socket, and verify cgroups and `/proc` contain no fixture processes. Preserve failed evidence and stop rather than broad cleanup if ownership becomes ambiguous.

This would prove at most **mode A**, isolated local transport. **Mode B**, useful external-provider traffic, requires a separate explicit egress policy and test covering direct connections that ignore proxy variables. No proxy allowlist, extra network service or provider call is authorized by this experiment.

## Specific security blockers

1. A user-manager socket owned by the same UID as Phi is accessible and replaceable by other processes of that UID, even with `0700`/`0600` modes. Filesystem permissions therefore cannot establish **Phi-only** access or prevent a same-UID socket replacement. The fixture has no client-side attestation of the connected peer after `connect`; checking only pathname, response or prior process metadata leaves a substitution race. A protected socket/credential boundary or a comparably strong peer-attestation design requires a separate Main security decision and host approval. The test must deliberately try a same-UID substitute before claiming anti-spoof.
2. The current Pi OpenAI-compatible client is not wired to Unix sockets. The exposed custom provider API is a possible implementation route, not a verified one; implementing it would alter the provider adapter and requires a separate scoped decision/test before any daily use.
3. Whether the official proxy joins the backend namespace on this user-manager host, and whether a production OmniRoute service can start there without sandbox regression or IPC/network side effects, remain runtime UNKNOWN until a separately authorized fake-service experiment and later product-specific validation.

No on-demand hook, stable launcher, routing, auth, Second Brain, SearXNG, OmniRoute installation or service was changed. Autostart remains disabled and manual-only preference unchanged.
