# Phase 38 — plugin framework V2 boundary

Status: **DEFERRED FOR SAFETY**. No capability manifest or new plugin was installed, because the current Pi 0.85.1 extension loader does not provide a pre-import filesystem/network/process confinement boundary. A manifest checked only by Overdrive after loading would be descriptive, not enforcement, and would falsely imply that an installed plugin is safe.

The local installed Pi source shows `loadExtension()` resolves a path, calls `loadExtensionModule()`, then initializes the factory with `ExtensionAPI` (`dist/core/extensions/loader.js`, lines 465–485 in the inspected installation). Module top-level code therefore executes before registration/Tool Governor policy. The loader iterates enabled extension paths in the same process (`loadExtensionsInternal`, lines 498–519); the resource loader passes merged CLI/package paths into it (`dist/core/resource-loader.js`, lines 316–320, 424–447). These are local-runtime facts, not claims about a future Pi version.

A bounded offline Pi 0.85.1 fixture in `tests/fixtures/plugin-host-authority.ts` proved the consequence: at module import time, before its factory registered even a command, it could stat harmless `/etc/hostname` and spawn a no-op Node process. `benchmarks/overdrive-vs-omp/plugin-boundary.mjs` recorded PASS for both probes, zero model/tool/network/external-provider calls, and complete temporary cleanup. The fixture is **not** in `package.json`'s Pi extension list; package validation rejects accidental registration. No credential path/content or network endpoint was accessed. This demonstrates filesystem/process host authority, not an exhaustive network exploit test.

The existing Overdrive selected packages are pinned and policy-reviewed, but their extension code is still trusted host code. Task/Tool Governor, safe_exec, Bubblewrap for wrapped commands, and Council/Worker restrictions do not constrain arbitrary top-level code inside a separately installed Pi extension. `config/packages.json` is an inventory and pin set, not an OS sandbox. A capability manifest declaring tools, filesystem, network, process, platform and hooks would be useful only after the host enforces it before importing plugin code.

A reliable V2 would require a separate least-privilege process/namespace per untrusted plugin (or an upstream loader security primitive), validated manifest before process start, a narrow message protocol, controller-granted capabilities, exact filesystem/network/process limits, hook priority that cannot replace core security, and tests that a malicious fixture is denied at import/runtime while legitimate tools continue. This cannot be implemented as a thin in-process Overdrive extension without weakening or misrepresenting the boundary. Therefore no manifest-only framework, third-party plugin activation, route change or provider call was added in Phase 38.
