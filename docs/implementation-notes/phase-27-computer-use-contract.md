# Phase 27 checkpoint: cross-platform Computer Use contract, no host authority

Phase 27 now has one platform-neutral internal `ComputerUseController` contract for `screenshot`, `inspect`, `click`, `type`, `key`, `scroll`, and `focus`. It is **not** a Pi model tool, a native Linux/Windows backend, or a claim that host Computer Use works. Package validation explicitly rejects registration of a host-computer extension. Both Linux and Windows default to `UNAVAILABLE` for every operation until a separately reviewed native broker exists.

The contract requires a controller-selected target with application, window, process, generation, bounds, and ordinary/non-sensitive classification. Each request has an exact action digest and a fresh per-action approval decision from a trusted broker. The target and optional accessibility element are re-resolved after approval. Coordinate actions additionally require a recent captured-frame digest, in-bounds coordinates, and a fresh backend frame comparison; stale frames fail closed. Session/action lifetimes are bounded, concurrent actions denied, and revocation aborts in-flight approval/backend calls. Type length and keys are allowlisted. The returned receipt contains only action/target/frame/artifact digests and status, not typed text, screenshot bytes, accessibility contents, prompts, or credentials. Capture/inspection results must be classified `REDACTED_SAFE` before a success receipt.

These are controller-level checks, **not yet OS enforcement**. A future native backend must itself bind an OS target, honor abort and timeout, classify/redact content before private artifact storage, and prove the approved action cannot fall through to another window. An injected fixture backend is not evidence that the host can safely perform the action.

## Current-host and platform evidence

- Read-only `busctl --user introspect org.freedesktop.portal.Desktop /org/freedesktop/portal/desktop` on this Linux session: Screenshot interface version 2 with `AvailableTargets=0`; ScreenCast exists; RemoteDesktop interface is absent; InputCapture reports `SupportedCapabilities=0`. `grim` and `slurp` are present, while `wtype` and `ydotool` are absent. No screenshot or input command was executed. A raw compositor/screen path would not prove the required target and sensitive-content boundary, so all host capabilities remain `UNAVAILABLE`.
- The [XDG Screenshot portal documentation](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.impl.portal.Screenshot.html) describes version 3's explicit target kinds, including user-selected windows; the active portal here is only version 2 and advertises no targets. The [RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) defines an approved session and input path, but that interface is absent here.
- On Windows, [UI Automation guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-usefortesting) treats runtime IDs as opaque and potentially reused, so a backend must revalidate identity rather than trust a stale selector. [Windows Graphics Capture](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture) offers user-picked window/display capture, but no Windows backend or Windows host/CI execution was performed. Windows status is `NOT_RUN`, not `REAL_HOST_VERIFIED`.

## Validation and disposition

Eight deterministic contract tests pass across Linux and Windows fixture backends: unavailable defaults, per-action approval, target/element replacement, stale frames, malformed/global/shell-like input, sensitive target/capture denial, metadata-only receipts, and revocation during consent and execution. The authoritative Expansion gate passes 474/474 tests plus syntax, installed-Pi TypeScript, package and secret validation. These are unit/fixture results, not native desktop integration tests. No host screen was captured, no host input was sent, no provider was called, and extra monetary cost was €0.

Phase 27 is **PARTIAL/DEFERRED FOR SAFETY**. The API/security contract is implemented and unit-verified, but Linux and Windows native backends, trusted approval UI, accessibility/capture redaction broker, private image lifecycle, and actual host validation remain missing. Do not register a `computer_use` schema or turn on raw desktop tools merely to claim parity. The earliest safe native slice would be an independently reviewed target-bound screenshot-only broker with user-visible approval and pre-publication redaction; it must not imply click/type rights.
