# Phase 39 — cross-platform portability boundary

Status: **PARTIAL / WINDOWS DEFERRED**. The current autonomous implementation is verified on Linux x86_64, not on native Windows x86_64. Its security is tied to Linux Bubblewrap/user namespaces, `/proc` process identity, POSIX file ownership/modes, shell scripts and pinned Linux DAP/LSP/browser runtimes. The Phase 27 `ComputerUseController` has a platform-neutral action/approval/target/frame contract with Linux and Windows fixtures, but both native computer backends remain unavailable. A common interface does not prove host isolation or functionality.

The safe Phase 39 change is an early bootstrap preflight. `scripts/prerequisites.sh` now checks the actual `uname` kernel/architecture through `scripts/platform-preflight.sh` **before** considering `--install-system` or `--install-pi`. Linux x86_64 proceeds unchanged; native Windows-like Git Bash/MSYS/Cygwin, Darwin, ARM Linux and other targets receive a clear unsupported-host error before the bootstrap installs or alters anything. This is an operator safety check, not a malicious-host security barrier or a Windows backend. Directly invoking arbitrary Pi package components outside bootstrap is not thereby made portable.

The deterministic fixture tests Linux acceptance and Windows/other-host denials, checks the preflight ordering, and the real Linux host passed the read-only prerequisites command with Pi 0.85.1 and Node 22.23.2. The authoritative package gate passed 515/515 plus syntax, TypeScript and package validation. No Windows machine was used; `REAL_HOST_VERIFIED` for Windows remains **NOT_RUN**. No Linux sandbox flag, worktree policy, provider route, credential, package, or installed Pi configuration changed.

A native Windows path requires separately reviewed least-privilege process/container and filesystem/network restrictions, process-tree/job cleanup, canonical NT path/ACL checks, collision-free worktree/runtime identities, local browser/profile isolation, pinned platform runtimes, receipt equivalence and end-to-end validation on an actual Windows x86_64 host. It must live behind an explicit backend interface while the existing Linux implementation remains intact. Do not substitute a shell/PowerShell wrapper for Bubblewrap or infer support from cross-platform JavaScript syntax and fixture tests.
