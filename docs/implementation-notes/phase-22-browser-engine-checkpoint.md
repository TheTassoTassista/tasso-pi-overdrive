# Phase 22 checkpoint: governed local browser actions

Historical partial checkpoint. Superseded by [Phase 22 completion](phase-22-browser-engine-completion.md) at functional commit `5701876`; the limitations below describe the earlier `58d96a5` state, not the current confined engine.

This checkpoint tightens the existing pinned `pi-agent-browser-native@0.6.6` and `agent-browser@0.36.0` integration. It does not install another browser plugin, add a model-facing schema, alter provider routes, or change normal interactive Pi browsing. In an Overdrive-managed autonomous worktree, `extensions/safety.ts` invokes `validateAllocatedBrowserCall` before `agent_browser` execution. Task Governor still requires explicit browser intent; Tool Governor still treats the browser as high-risk conditional.

The allocated path now accepts only `args`, optional bounded `timeoutMs`, and the browser plugin's `sessionMode`. Every call must name the runtime allocation's exact session. Initial `open` must bind its exact private profile, use `sessionMode=fresh`, and target `http://127.0.0.1:<reserved-port>/...`. Follow-ups allow only compact/interactive snapshot, simple ref/ID click and fill, text wait, bounded getters, one screenshot to the fixed private runtime-state pathname, and exact session close. Alternate profile/session, `file:` or external initial navigation, JavaScript evaluation, CDP attach, scripts/jobs/batches, auth/cookies/storage, upload/download, network routing, arbitrary output paths, and broad close are rejected before the plugin starts. Screenshot destinations must be absent under the canonical private state directory; cleanup removes that state with the managed worktree.

The real local Pi smoke uses the Ultra package from this worktree, the already-installed browser plugin, an owner-local deterministic provider profile, and a temporary Git repository. It first proves a forbidden `eval` produces an error without materializing a browser profile. It then starts a loopback fixture on the allocation's reserved port and executes eight real browser calls: open, interactive snapshot, fill, click, wait, DOM text read, PNG screenshot, close. It verifies the changed DOM text, PNG signature, private profile materialization, and removal of browser process, worktree, port reservation, allocation state, and temporary files. No external provider or paid model is used. OMP remains source-inspected only; Bun >=1.4 is unavailable.

This is a **checkpoint, not a network-containment claim**. The pinned browser's `--allowed-domains` switch refuses `--profile`, and a port-qualified allowlist is not supported. While the first navigation is restricted, page-driven navigation or subresources may still reach other network origins, and the native plugin process is not inside Bubblewrap. A same-UID adversary may race a screenshot path after the private-directory check. Binary screenshots are private runtime artifacts, not yet content-addressed Artifact Store objects. Controlled downloads and bounded network metadata are deliberately absent. Until these gaps have an enforced solution, allocated browser automation should be used only against trusted local UI fixtures, not untrusted pages or credentialed/internal web applications.

A separate feasibility probe launched the exact installed `agent-browser@0.36.0` binary and its installed Chromium 152.0.7977.82 inside a networkless `bwrap --unshare-all --die-with-parent` mount namespace and successfully opened `about:blank`; loopback was up inside that namespace. This proves a browser process can start behind the OS network boundary, **not** that Pi can yet drive a persistent confined session. The next implementation should keep one lazy, bounded browser runner inside a single namespace for the entire UI interaction, expose only a constrained local fixture server there, and prove process/namespace teardown and forbidden-origin failure before replacing the current allocated plugin path.
